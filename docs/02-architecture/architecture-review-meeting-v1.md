## 3. 评审员 A：可修改性与可维护性草案

### 3.1 架构风格声明

**风格：分层架构 + 精简端口适配器。**

选择该风格是为了让认领状态、争议权限和匹配规则集中在可独立测试的业务核心中，同时把 SQLite、文件备份、图片存储和模拟校园卡认证隐藏在适配器之后。该结构优先响应可维护性、信息隐藏和关键易变点，但不引入网络服务、消息队列或微服务。

### 3.2 组件与职责

| 模块/组件 | 职责 | 关键依赖或通信方式 | 隔离的易变点 | 关联需求 |
|---|---|---|---|---|
| `LostAndFound.App` 桌面壳与页面 | 提供 WinForms 窗口、导航、键盘焦点顺序和屏幕阅读器元数据 | 通过应用用例接口同步调用 Core；不直接访问 SQLite | 界面布局变化、高对比度和无障碍交互调整 | FR-A11Y-001 至 006, NFR-A11Y-001 至 006 |
| `AuthenticationService` | 注册、登录、密码修改和本地模拟校园卡认证流程 | 依赖用户仓储接口、密码哈希端口、身份模拟端口 | 未来替换校园卡验证方式 | FR-AUTH-001 至 008 |
| `ListingService` | 发布、编辑、审核、浏览、搜索和状态变更 | 依赖信息仓储、审核记录、授权策略 | 信息字段和审核规则变化 | FR-POST-001 至 008, FR-BROWSE-001 至 005 |
| `MatchingService` | 生成可解释候选、排序和忽略关联 | 依赖 `IMatchPolicy`；纯业务计算 | 权重、匹配维度、阈值或推荐方式变化 | FR-MATCH-001 至 005 |
| `ClaimService` | 发起、取消、完成认领及关闭其他进行中认领 | 调用领域状态机、认领仓储和审计端口；事务由工作单元管理 | 认领步骤和完成规则变化 | FR-CLAIM-001 至 006 |
| `DisputeService` | 提交争议、管理员调查、补充说明和关闭争议 | 依赖争议仓储、会话读取端口、授权策略和审计端口 | 仲裁角色、申诉层级和聊天访问规则变化 | FR-DISPUTE-001 至 004, FR-CLAIM-007 |
| `AdminService` | 审核、删除、封禁和统计 | 依赖管理仓储、授权策略、审计端口 | 管理权限与审核流程变化 | FR-ADMIN-001 至 005 |
| `BackupService` | 自动和手动备份、清理、完整性校验、恢复前保护 | 通过 `IBackupStore` 接口访问本地文件 | 备份周期、数量、加密、路径和校验方式变化 | FR-BACKUP-001 至 005 |
| `Domain` | 保存信息、认领、争议和账号状态机，执行跨实体业务规则 | 纯 .NET 类型；不依赖 UI 或数据库 | 状态迁移和权限规则变化 | NFR-REL-002 至 003 |
| `Ports` | 定义仓储、匹配策略、身份验证、审计、备份和文件存储接口 | 接口契约；同步调用 | 外部实现替换和测试替身 | NFR-MAIN-001 至 002 |
| `Infrastructure` | 实现 SQLite 仓储、事务、数据库迁移、模拟认证、本地图片和备份文件 | 实现 Ports，依赖 SQLite 和本地文件系统 | 数据库、文件系统或认证适配方式变化 | NFR-SEC-001 至 004, NFR-PRIV-001 至 002 |
| `Tests` | 覆盖状态机、权限、匹配、备份和关键 UI 可访问流程 | 引用 Core 与 Infrastructure | 质量回归 | NFR-REL-001 至 003, NFR-A11Y-001 至 006 |

### 3.3 关键通信与依赖方向

```text
WinForms UI -> Application Use Cases -> Domain
                         |               |
                         v               v
                       Ports <------ Infrastructure
```

- 所有调用均在单进程内同步完成。
- UI 只能调用应用服务，不直接执行 SQL。
- Domain 不依赖 UI、SQLite 或文件系统。
- Infrastructure 实现由 Core 定义的端口，依赖方向指向 Core。
- 认领完成和备份恢复通过工作单元或事务边界保持数据一致。

### 3.4 对质量需求的响应

| 质量需求 | 草案 A 的响应 |
|---|---|
| NFR-MAIN-001 业务与界面分离 | Domain 和 Application 可独立于 WinForms 测试 |
| NFR-PRIV-001 管理员访问可审计 | 争议调查通过统一授权与审计入口，避免各页面自行判断 |
| NFR-A11Y-001 至 006 | UI 层统一封装焦点、无障碍名称和高对比度行为 |
| NFR-REL-002 数据一致性 | 应用服务定义事务边界，SQLite 适配器执行原子提交 |
| FR-MATCH-002 至 003 易变 | 匹配规则通过策略端口隔离 |
| FR-BACKUP 系列易变 | 备份调度与文件存储通过独立服务/端口隔离 |

### 3.5 主要代价

- 项目结构与接口数量较多。
- 小规模课程项目中存在抽象收益不明显的部分。
- 需要学生理解依赖方向和端口适配器，而不是直接把 SQL 写在窗体事件中。

## 4. 评审员 B：可交付性与避免过度设计草案

### 4.1 架构风格声明

**风格：特性优先的分层单体。**

选择该风格是为了在单机 WinForms 课程项目中减少工程拆分和依赖注入成本，让一个可执行项目即可完成演示。模块按业务特性组织，通过统一的数据访问类访问 SQLite，只保留对测试和易变点确有价值的服务边界。

### 4.2 组件与职责

| 模块/组件 | 职责 | 关键依赖或通信方式 | 隔离的易变点 | 关联需求 |
|---|---|---|---|---|
| `Forms` | 主窗口、登录、信息、认领、管理和备份页面 | 直接调用同一项目中的业务服务 | 界面布局变化 | FR-BROWSE, FR-CLAIM, FR-ADMIN |
| `AuthFeature` | 注册、登录、密码与模拟校园卡验证 | 调用 `SqliteDatabase` 和密码工具 | 校园卡模拟规则变化 | FR-AUTH-001 至 008 |
| `ListingFeature` | 发布、审核、浏览和搜索信息 | 调用 `ListingRepository` | 信息字段和查询条件变化 | FR-POST, FR-BROWSE |
| `MatchingFeature` | 固定字段权重、候选排序和忽略 | 调用 `ListingRepository`；具体规则类封装算法 | 匹配权重变化 | FR-MATCH-001 至 005 |
| `ClaimFeature` | 认领会话、消息、完成和取消 | 调用 `ClaimRepository`、`MessageRepository` | 认领步骤变化 | FR-CLAIM-001 至 006 |
| `AdminFeature` | 审核、用户管理、统计、争议 | 调用各仓储和 `AuditLogger` | 管理操作变化 | FR-ADMIN, FR-DISPUTE |
| `BackupFeature` | 定时备份、手动备份、清理和恢复 | 直接使用本地文件和 `SqliteDatabase` | 备份策略变化 | FR-BACKUP-001 至 005 |
| `Data` | 集中管理连接、事务、SQL 和数据库初始化 | 被各 Feature 直接调用 | 数据库结构变化 | NFR-REL-002, NFR-SEC-002 |
| `AccessibilitySupport` | 统一设置控件名称、焦点顺序、系统颜色和提示 | 被 Forms 调用 | 无障碍实现方式变化 | FR-A11Y, NFR-A11Y |

### 4.3 关键通信与依赖方向

```text
Forms -> Feature Services -> Data / AccessibilitySupport
```

- 单个 `LostAndFound.App` 项目承载主要代码，按目录区分特性。
- Feature 之间不建立事件总线，直接调用必要服务。
- 数据访问集中到 `Data`，但业务服务可感知 SQLite 仓储类型。
- 匹配算法、备份流程和匿名访问规则各自封装为独立类，避免全部写在窗体中。

### 4.4 对质量需求的响应

| 质量需求 | 草案 B 的响应 |
|---|---|
| NFR-MAIN-001 业务与界面分离 | 使用业务服务类隔离主要逻辑，虽然同属一个项目 |
| NFR-PRIV-001 管理员访问可审计 | `AdminFeature` 通过统一 `AuditLogger` 写入日志 |
| NFR-A11Y-001 至 006 | `AccessibilitySupport` 统一常见控件设置 |
| NFR-REL-002 数据一致性 | `SqliteDatabase` 提供统一事务方法 |
| FR-MATCH 易变 | `MatchingFeature` 集中保存权重和排序逻辑 |
| FR-BACKUP 易变 | `BackupFeature` 集中保存备份和恢复流程 |

### 4.5 主要代价

- Feature 与具体 SQLite 实现耦合，单元测试需要数据库或测试数据。
- 随着模块增长，单一项目可能出现循环依赖和边界模糊。
- 多处直接调用同一数据访问层，权限与审计一致性依赖开发纪律。
- 如果更换数据库、认证方式或匹配算法，改动范围大于草案 A。

## 5. 中立书记员：分歧点清单

### 5.1 书记员提示词

```text
请以中立书记员身份比较草案 A 和草案 B。
只从解耦、信息隐藏、关注点分离、抽象和可修改性角度结构化呈现分歧，
不推荐方案，不评判优劣。分歧点不超过 4 条，并为每条说明原因。
```

### 5.2 分歧点

| 序号 | 分歧点 | 草案 A | 草案 B | 相关设计原则 | 分歧原因 |
|---|---|---|---|---|---|
| D-01 | 数据访问边界的深度 | 业务核心通过仓储端口访问 SQLite，基础设施位于独立程序集 | Feature 服务使用集中数据类，可感知具体仓储类型 | 信息隐藏、解耦 | A 优先隐藏数据库实现并降低替换成本；B 优先减少项目与接口层级 |
| D-02 | 匹配规则的扩展方式 | 通过 `IMatchPolicy` 端口替换得分与排序策略 | 在 `MatchingFeature` 中集中实现固定规则 | 抽象、模块化 | A 针对匹配权重和维度变化建立替换点；B 认为变化范围有限，只需集中代码 |
| D-03 | 权限与审计的组织位置 | 授权策略和审计端口由领域/应用层统一使用 | 管理功能调用统一审计类，权限检查由相关 Feature 执行 | 关注点分离、信息隐藏 | A 降低各功能权限规则不一致的风险；B 减少跨层调用和初始实现复杂度 |
| D-04 | 备份与文件的隔离方式 | `BackupService` 通过 `IBackupStore` 隐藏文件细节 | `BackupFeature` 直接处理文件和数据库快照 | 信息隐藏、可修改性 | A 便于替换备份路径、加密和存储方式；B 减少为单一实现引入接口的成本 |

## 6. 学生裁决

| 序号 | 裁决对象 | 选项 | 决策 | 理由 |
|---|---|---|---|---|
| 1 | 总体方案 | 方案 A / 方案 B / 合并折中 / 全部拒绝 | 合并折中 | 保留轻量可交付结构，同时隔离关键易变点并集中权限审计 |
| 2 | 若合并折中，基底方案 | 以 A 为基底 / 以 B 为基底 | 以方案 B 为基底 | 课程单机项目不需要完整端口适配器结构，方案 B 更符合交付规模 |
| 3 | 从另一方案借用的结构 | 见 6.1 | 部分借用方案 A | 只引入能直接响应关键易变点和质量要求的边界 |

### 6.1 合并结果

| 借用项 | 具体结构 | 来源 | 决策依据的软件设计原则 |
|---|---|---|---|
| 认领和争议规则隔离 | 独立 `WorkflowRules`，集中实现信息、认领、争议和账号状态迁移 | 方案 A | 关注点分离、信息隐藏 |
| 关键易变点端口 | 引入 `IMatchPolicy`、`IIdentityVerifier`、`IBackupStore` 三个最小接口 | 方案 A | 抽象、可修改性 |
| 权限与审计集中 | 使用统一 `AuthorizationPolicy` 和 `AuditService`，管理敏感访问 | 方案 A | 关注点分离、安全内聚 |
| 特性优先组织 | 以 Windows、认证、发布、匹配、认领、管理、备份、公共支持为目录边界 | 方案 B | 模块化、可交付性 |
| 单项目轻量部署 | 主要功能位于同一 WinForms 应用项目，通过少量测试项目验证核心规则 | 方案 B | 避免过度设计、可交付性 |

### 6.2 已拒绝或未采用

| 内容 | 来源 | 拒绝理由 |
|---|---|---|
| 为全部仓储和数据访问都建立端口抽象 | 方案 A | 只有单一 SQLite 实现，全面抽象会增加课程项目复杂度且没有直接收益 |
| 业务 Feature 直接执行 SQL 和文件操作 | 方案 B | 会使状态规则、权限审计和备份恢复难以隔离测试 |
| 将匹配权重直接写死在窗体或查询代码中 | 方案 B | 无法响应已识别的匹配规则易变点 |
| 将备份、审计和权限判断分散在各管理页面 | 方案 B | 易造成规则不一致和敏感操作漏记 |

## 7. 当前结论

学生选择以方案 B 为基底进行合并折中，并从方案 A 借用状态规则隔离、三个关键易变点端口以及统一的权限审计入口。下一阶段必须在本次裁决基础上增加至少一项关键细节或局部调整，不能原样照搬评审会结论。
