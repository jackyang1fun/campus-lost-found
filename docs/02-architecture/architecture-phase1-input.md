# 软件架构设计阶段 1：项目开发上下文

> 本文件由项目负责人独立填写，作为架构评审会议的学生输入。阶段 1 不设计模块图或分层方案。

## 1. 项目与个人切片

- 项目名称：校园失物招领系统
- 提交方式：团队项目个人切片
- 本次负责的功能切片：失物认领子系统、系统管理子系统
- 主要使用者：本校学生、教职工、系统管理员

## 2. 需求构思

请用自己的话概括系统要解决的问题、预期价值和核心使用场景：
本系统用于解决校园内物品丢失、拾获后信息分散、查找沟通不便的问题；为失主和拾获人提供线上发布、智能匹配、匿名沟通、认领流程管理能力，管理员负责信息审核、争议处理和数据备份维护，提升校园失物找回效率。

## 3. 项目边界与非目标

### 3.1 项目边界
1. 实现失物、招领信息的智能匹配，对相似度较高的记录进行推荐
2. 提供匿名聊天功能，支持失主与拾获人沟通交接细节
3. 完整覆盖认领流程：发起认领、确认、标记完成
4. 管理员可以审核发布信息、处理认领纠纷争议
5. 支持本地 SQLite 数据库定期备份，保障基础数据安全
6. 校园卡身份认证为本地模拟校验，不接入学校一卡通真实接口
7. 程序为单机 WinForms 桌面程序，运行在 Windows10/11 x64 平台

### 3.2 非目标
1. 不接入学校官方一卡通认证接口，不完成真实身份核验
2. 不做网络多端网页部署，仅单机离线运行，不支持多客户端联网协同
3. 不实现短信、微信等外部消息推送通知
4. 不实现线下物品寄存、实物托管功能，仅做线上信息对接
5. 不支持复杂图片 AI 识别，仅做简单文字匹配

## 4. 功能需求

请从 `requirements-specification-v2.1-final.md` 中选择与本人切片直接相关的功能需求，并说明选择理由。引用需求 ID，但不要粘贴整份 SRS。

| 需求 ID | 功能摘要 | 为何属于本次切片 |
|---|---|---|
| FR-MATCH-001 | 仅对已审核通过的失物与招领信息建立候选关系 | 基础关联匹配是认领子系统的前置能力 |
| FR-MATCH-002 | 按分类、地点、描述关键词和时间接近程度计算可解释匹配依据 | 决定候选配对结果能否被用户理解和验证 |
| FR-MATCH-003 | 对候选进行排序并最多显示 10 条 | 控制候选规模和展示逻辑 |
| FR-MATCH-004 | 匹配结果仅作建议，必须由用户主动发起认领 | 防止系统自动改变业务状态 |
| FR-MATCH-005 | 用户可以忽略候选关联 | 为后续匹配体验调整保留空间 |
| FR-CLAIM-001 | 用户可从已通过且未解决的信息发起认领 | 认领流程入口 |
| FR-CLAIM-002 | 认领创建双方专属匿名会话 | 保护认领双方身份信息 |
| FR-CLAIM-003 | 认领双方发送和查看文字消息 | 支持交接细节协商 |
| FR-CLAIM-004 | 协商阶段可继续沟通或取消认领 | 管理认领生命周期 |
| FR-CLAIM-005 | 信息发布者确认物品完成交接 | 认领完成的关键判定动作 |
| FR-CLAIM-006 | 完成一项认领后解决信息并关闭其他进行中认领 | 保证业务状态的一致性 |
| FR-CLAIM-007 | 管理员只能在争议或审计场景查看真实账号和会话 | 处理隐私与追责之间的边界 |
| FR-DISPUTE-001 | 认领双方可提交争议 | 处理认领过程中的异议 |
| FR-DISPUTE-002 | 管理员可查看争议相关的真实账号、认领记录和会话 | 支撑调查与责任认定 |
| FR-DISPUTE-003 | 管理员记录结论并关闭争议 | 形成完整的争议闭环 |
| FR-DISPUTE-004 | 管理员可要求双方补充说明 | 支持复杂争议的进一步调查 |
| FR-ADMIN-001 | 管理员登录并访问管理功能 | 系统管理请求的权限入口 |
| FR-ADMIN-002 | 管理员审核通过或驳回待发布信息 | 控制公开内容的准入 |
| FR-ADMIN-003 | 管理员删除虚假或违规信息 | 维护公开信息质量 |
| FR-ADMIN-004 | 管理员查看用户并封禁违规用户 | 控制平台使用权限 |
| FR-ADMIN-005 | 管理员查看失物、招领、已解决和待审核数量 | 提供基础运营状态 |
| FR-BACKUP-001 | 应用每天首次启动时自动备份 | 保障本地数据安全 |
| FR-BACKUP-002 | 保留最近 7 份自动备份 | 限制备份空间并形成恢复窗口 |
| FR-BACKUP-003 | 管理员可手动创建备份 | 支持演示前或重要操作前的保护 |
| FR-BACKUP-004 | 管理员可从备份恢复数据 | 验证备份具有实际恢复价值 |
| FR-BACKUP-005 | 系统校验备份完整性 | 防止损坏备份覆盖有效数据 |

## 5. 质量需求

请列出会实际影响架构权衡的质量需求及量化指标。

| 质量属性 | 量化要求 | 来源需求 ID |
|---|---|---|
| 性能 | 10,000 条信息下搜索或筛选不超过 1 秒；启动不超过 5 秒 | NFR-PERF-001, NFR-PERF-002 |
| 数据完整性 | 连续运行 2 小时并执行至少 200 次核心操作，不崩溃、不丢失已提交数据 | NFR-REL-001, NFR-REL-002 |
| 安全性 | 密码哈希保存、校园卡号唯一、敏感操作进行角色校验 | NFR-SEC-001 至 NFR-SEC-004 |
| 隐私与可审计性 | 普通用户匿名；管理员访问身份或聊天记录时写入审计日志 | NFR-PRIV-001, NFR-PRIV-002 |
| 无障碍 | Narrator 和键盘可完成核心流程；支持高对比度、合理焦点与文字提示 | NFR-A11Y-001 至 NFR-A11Y-006 |
| 可维护性 | 业务规则与界面分离；核心规则具有自动化测试 | NFR-MAIN-001, NFR-MAIN-002 |

## 6. 开发约束

请填写真实约束。团队人数或工期尚未确定时，可以写“待确认”，不要编造。

| 约束 | 当前情况 | 对架构的影响 |
|---|---|---|
| 平台 | Windows 10/11 x64 | 采用 Windows 原生桌面控件，重点验证 Narrator、键盘焦点和高对比度 |
| 部署形态 | 单机离线桌面应用 | 不设远程服务，SQLite 成为唯一数据源，备份与恢复由本地进程管理 |
| 开发环境 | VSCode + .NET 10 | 采用可由 CLI 构建和测试的工程结构，减少对图形设计器的依赖 |
| 团队与工期 | 待确认 | 架构应在不引入远程服务的前提下控制复杂度，并允许分期实现 |
| 技术与数据 | WinForms + SQLite | 使用分层边界隔离界面、业务规则、数据访问和文件备份 |
| 外部接口 | 校园卡认证采用本地模拟 | 认证实现需要与业务规则隔离，避免未来切换接口时影响认领与管理流程 |

## 7. 关键易变点

请列出 2 至 3 个最可能在开发中变化的点，并说明可能变化的方向。不要在本阶段给出模块拆分方案。

1. 易变点：
   - 可能变化：当前按分类、地点、关键词和时间加权得分，后续可能调整权重、增加物品特征、地点类型或人工阈值，也可能取消自动推荐。
   - 受影响的需求：FR-MATCH-002、FR-MATCH-003
2. 易变点：
   - 可能变化：当前仅管理员在争议审计时查看聊天和真实信息，后续可能增加仲裁角色、申诉层级、聊天限制或办结后脱敏归档。
   - 受影响的需求：FR-DISPUTE-001 至 FR-DISPUTE-004、FR-CLAIM-007
3. 易变点：
   - 可能变化：当前每日自动备份并保留 7 份，后续可能调整备份时间、数量、加密、外部路径或恢复前校验规则。
   - 受影响的需求：FR-BACKUP-001 至 FR-BACKUP-005
