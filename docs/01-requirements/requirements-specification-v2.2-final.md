## 1. 引言

### 1.1 编写目的

本文档用于定义 Lost and Found System 的业务目标、系统边界、用户角色、功能需求、非功能需求、业务规则和验收标准，作为后续架构设计、数据库设计、编码、测试和需求变更追溯的依据。

### 1.2 项目目标

系统为校园失物与招领信息提供一个统一、可演示的桌面平台，使用户能够在同一台 Windows 电脑上完成以下活动：

1. 使用模拟校园卡号完成注册、认证和登录。
2. 发布、审核、浏览、搜索和管理失物或招领信息。
3. 根据分类、地点、关键词和时间接近程度查找候选关联信息。
4. 发起认领，在匿名聊天中协商交接，并确认认领结果。
5. 由管理员处理信息审核、用户管理、数据备份和认领争议。
6. 使用键盘、屏幕阅读器和高对比度模式完成全部核心任务。

系统定位为课程作业和个人演示版本，不代表学校已部署的正式在线服务。

### 1.3 术语与缩写

| 术语 | 定义 |
|---|---|
| 失物信息 | 物品所有者发布的物品遗失信息 |
| 招领信息 | 物品拾获者发布的物品招领信息 |
| 信息发布者 | 某条失物或招领信息的创建者 |
| 认领发起人 | 对某条已发布信息发起认领的普通用户 |
| 认领双方 | 信息发布者与认领发起人 |
| 匿名编号 | 系统为认领双方分配的、仅在本认领中显示的替代称呼 |
| 基础关联匹配 | 依据可解释规则生成候选配对，不做自动认领或机器学习推断 |
| RTM | 需求可追溯性矩阵 |
| Narrator | Windows 自带屏幕阅读器 |

## 2. 系统边界

### 2.1 首期范围

首期版本包含：

- 本地模拟校园卡绑定与认证。
- 普通用户和管理员两类正式角色，以及未登录游客访问方式。
- 失物发布、招领发布、管理员审核、浏览、搜索和详情展示。
- 基于规则的基础关联匹配。
- 认领发起、匿名聊天、交接确认和状态更新。
- 信息管理、用户管理、基础统计和管理员初始化。
- 每日自动备份、手动备份和恢复。
- 认领争议提交、管理员处理和管理员审计日志。
- 面向视障和低视力用户的桌面无障碍支持。

### 2.2 明确非目标

以下内容不属于首期范围：

- 接入学校真实校园卡、统一身份认证或教务系统接口。
- Web、移动端、云部署和互联网发布。
- 跨电脑实时通信、局域网多人协作或真实即时消息服务。
- 图片识别、语义大模型匹配、机器学习训练和自动确认认领。
- 短信、邮件、支付、快递和校外机构对接。
- 对发布人进行真实身份的人工线下核验。
- 与真实生产环境等价的数据保留、灾备和安全合规认证。

### 2.3 运行与分发边界

1. 系统以 Windows x64 桌面应用发布，支持 Windows 10/11。`【Revised】`
2. 应用采用自包含发布方式，目标电脑无需预装 .NET 运行时。`【VP-Adopted】`
3. 应用复制到不同电脑后可分别独立运行，每台电脑的数据相互隔离。
4. 应用不依赖互联网即可完成全部首期功能。
5. 数据最终存储在本机 SQLite 数据库，备份保存在应用可写的本地目录。
6. 可以通过同一台电脑上的不同账号演示多方业务，但不承诺跨设备通信。

## 3. 涉众与角色

### 3.1 涉众

| 涉众 | 关注点 |
|---|---|
| 失主 | 快速发布失物信息、查看匹配结果、确认找回、保护联系方式 |
| 拾获人 | 发布招领信息、识别失主、安全交接物品 |
| 普通用户/游客 | 无需复杂操作即可浏览和搜索公开信息 |
| 管理员 | 审核内容、处理争议、维护用户和数据安全 |
| 课程验收者 | 需求完整性、可测试性、协作记录、架构决策和可追溯性 |
| 视障或低视力用户 | 屏幕阅读器可读、键盘可操作、高对比度和焦点清晰 |

### 3.2 角色与权限

| 角色 | 权限 |
|---|---|
| 游客 | 浏览和搜索已审核通过的信息、查看公开详情；不能发布、认领或聊天 |
| 普通用户 | 游客权限；注册、登录、发布、管理自己的记录、发起认领、参与聊天、提交争议 |
| 管理员 | 审核和管理信息、管理用户、查看统计、备份与恢复、处理争议、执行审计 |

未登录用户可访问公开信息，注册、登录或认领操作会引导其先登录。`【VP-Adopted】`

## 4. 功能需求

优先级定义：

- `M`：首期必须完成，缺失时核心业务不成立。
- `S`：首期应完成；若与硬性质量要求冲突，可按学生最终裁决调整。
- `C`：可延后，不进入首期验收。

### 4.1 用户与认证

| ID | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-AUTH-001 | M | 用户注册时填写显示名称、校园卡号、联系方式和密码，并同意数据用途说明。 | 未勾选用途说明不能完成注册；说明至少包含采集目的、用途和范围。 |
| FR-AUTH-002 | M | 校园卡号采用本地模拟验证，一个校园卡号只能绑定一个普通用户账号。 | 使用重复卡号注册时被拒绝，数据库唯一约束生效。`【VP-Adopted】` |
| FR-AUTH-003 | M | 用户使用校园卡号和密码登录。 | 正确凭据可以进入主界面；错误凭据给出不含敏感信息的提示。 |
| FR-AUTH-004 | M | 登录会话在当前应用运行期间有效，退出登录或关闭应用后结束。 | 退出后不能继续执行受保护操作；应用不保存明文密码。`【Revised】` |
| FR-AUTH-005 | M | 用户可查看和修改显示名称、联系方式；修改后立即生效。 | 修改只影响本人账号，并在重新打开资料页后保持。 |
| FR-AUTH-006 | M | 用户可修改密码。 | 修改前需验证旧密码；新密码满足长度要求；修改后旧密码失效。 |
| FR-AUTH-007 | M | 用户可以注销账号。 | 二次确认后账号被禁用且不能继续登录；历史争议所需数据不被静默删除。`【VP-Adopted】` |
| FR-AUTH-008 | M | 系统在首次运行时提供管理员初始化流程。 | 未创建管理员前不能执行管理操作；初始密码不得以明文持久化。`【VP-Adopted】` |

### 4.2 失物与招领信息

| ID | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-POST-001 | M | 登录用户可以发布失物信息，字段包括物品名称、分类、发生时间、地点、描述、照片和联系方式。 | 必填字段完整时提交成功并进入待审核状态；缺失必填字段时有明确错误提示。 |
| FR-POST-002 | M | 登录用户可以发布招领信息，字段规则与失物信息一致。 | 新招领信息进入待审核状态，不能立即出现在公开列表。 |
| FR-POST-003 | M | 图片使用本地存储，支持常见图片格式，限制单个文件大小。 | 非图片文件或超过限制的文件被拒绝；公开详情可显示成功上传的图片。`【Revised】` |
| FR-POST-004 | M | 图片上传时要求填写替代文本。 | 屏幕阅读器能朗读图片用途或内容摘要，而不是只朗读文件名。`【VP-Adopted】` |
| FR-POST-005 | M | 管理员审核待发布信息，可通过或驳回。 | 通过后进入公开列表；驳回必须填写理由；发布者可查看驳回原因。 |
| FR-POST-006 | M | 发布者可以修改或撤销自己发布的信息。 | 修改后的已通过信息重新进入审核；撤销需要二次确认并保留审计记录。`【VP-Adopted】` |
| FR-POST-007 | M | 发布者可以标记物品已找回或已认领。 | 状态改为已解决；该信息不再接受新认领，但历史认领记录仍可查看。 |
| FR-POST-008 | M | 系统仅向游客和普通用户展示审核通过且未解决的信息。 | 待审核、驳回、已解决和已删除信息不出现在公开列表中。 |

### 4.3 浏览、搜索与详情

| ID | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-BROWSE-001 | M | 首页分别展示失物和招领信息。 | 两类信息有明确文字标签，不能只依赖颜色区分。 |
| FR-BROWSE-002 | M | 用户可按物品名称、描述、地点关键词搜索。 | 搜索不区分前后空格；无结果时显示明确空状态。 |
| FR-BROWSE-003 | M | 用户可按分类筛选，并可组合关键词搜索。 | 搜索和筛选条件同时生效；提供清除条件操作。 |
| FR-BROWSE-004 | M | 用户可查看信息详情。 | 详情显示状态、分类、时间、地点、描述、图片替代文本和可执行的下一步操作。 |
| FR-BROWSE-005 | S | 列表可按发布时间排序。 | 排序结果稳定，重新打开后仍能正确排序。 |

### 4.4 基础关联匹配

| ID | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-MATCH-001 | M | 系统仅对已通过审核的一条失物信息与招领信息生成候选关联。 | 不匹配待审核、驳回、已解决或已删除信息。 |
| FR-MATCH-002 | M | 匹配依据包括分类、地点关键词、描述关键词和时间接近程度。 | 每条候选显示至少两个可解释的匹配依据。`【VP-Adopted】` |
| FR-MATCH-003 | M | 候选结果按可解释得分排序，最多显示 10 条。 | 结果数量不超过 10；相同输入在相同数据下得到一致顺序。 |
| FR-MATCH-004 | M | 匹配结果只是建议，不自动改变信息或认领状态。 | 用户必须主动进入详情并发起认领。`【VP-Adopted】` |
| FR-MATCH-005 | S | 用户可关闭或忽略某条候选关联。 | 被忽略候选不再出现在当前用户的默认推荐中，但不影响其他用户。 |

### 4.5 认领与匿名沟通

| ID | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-CLAIM-001 | M | 登录用户可从已通过且未解决的失物或招领信息发起认领。 | 用户不能认领自己的信息；发起时必须填写 10 至 200 个字符的认领说明；同一用户对同一条信息只能存在一项进行中的认领。`【Revised】` |
| FR-CLAIM-002 | M | 发起认领后创建认领双方专属的匿名聊天会话。 | 双方只看到匿名编号，不自动显示真实姓名、校园卡号或联系方式。`【VP-Adopted】` |
| FR-CLAIM-003 | M | 发布者和认领发起人可在会话中发送和查看文字消息。 | 非参与者不能查看会话；消息在账号切换或重新打开会话后仍存在。 |
| FR-CLAIM-004 | M | 当认领处于协商阶段时，双方可以继续沟通或取消认领。 | 取消后不能继续发送新消息，会话转为只读并记录取消方与时间。 |
| FR-CLAIM-005 | M | 信息发布者可以确认物品已完成交接。 | 确认前要求二次确认；确认后认领状态变为已完成。`【VP-Adopted】` |
| FR-CLAIM-006 | M | 某条信息完成认领后，该信息变为已解决，其他进行中的认领自动关闭。 | 不允许对已解决信息发起新认领；其他申请方看到关闭原因。`【VP-Adopted】` |
| FR-CLAIM-007 | M | 管理员仅在处理相关争议或执行审计时可以查看真实账号和会话内容。 | 每次查看记录管理员、时间、相关争议和访问原因。`【VP-Adopted】` |
| FR-CLAIM-008 | M | 认领说明只对认领双方和管理员可见，并在发起认领时保存。 | 发布者在认领管理和聊天页均可查看认领说明；非参与者不能读取。`【VP-Adopted】` |

### 4.6 管理员功能

| ID | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-ADMIN-001 | M | 管理员可登录并查看管理功能。 | 普通用户无法访问管理员功能；未初始化管理员时提示先完成初始化。 |
| FR-ADMIN-002 | M | 管理员可查看待审核信息并执行通过或驳回。 | 两种操作均形成审计记录；驳回必须包含理由。 |
| FR-ADMIN-003 | M | 管理员可删除虚假或违规信息。 | 删除前进行二次确认；公开列表立即隐藏；管理端保留操作记录。 |
| FR-ADMIN-004 | M | 管理员可查看用户列表并封禁违规用户。 | 封禁必须填写原因；被封禁用户不能登录；解封操作同样记录审计。 |
| FR-ADMIN-005 | S | 管理员可查看失物总数、招领总数、已解决数量和待审核数量。 | 统计结果与数据库当前数据一致，刷新后更新。 |

### 4.7 备份与恢复

| ID | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-BACKUP-001 | M | 应用每天首次启动时自动创建一次备份。 | 同一天重复启动不重复创建自动备份；备份文件可识别日期。`【VP-Adopted】` |
| FR-BACKUP-002 | M | 保留最近 7 份自动备份。 | 第 8 份自动备份生成后，最旧自动备份被清理；手动备份不被自动清理。 |
| FR-BACKUP-003 | M | 管理员可以手动创建备份。 | 手动备份成功后显示文件名、时间和存储位置。 |
| FR-BACKUP-004 | M | 管理员可以从备份恢复数据。 | 恢复前二次确认，并先创建当前数据的安全副本；恢复后重启应用仍保留恢复结果。 |
| FR-BACKUP-005 | M | 系统验证备份文件完整性。 | 损坏或格式不正确的备份不能被恢复，并给出可读错误信息。 |

### 4.8 争议处理

| ID | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-DISPUTE-001 | M | 认领双方可以针对相关认领提交争议。 | 提交时必须选择原因并填写说明；无相关认领时不能提交。`【VP-Adopted】` |
| FR-DISPUTE-002 | M | 管理员可查看争议涉及的真实账号、认领记录和会话内容。 | 查看身份和聊天内容的行为写入审计日志。 |
| FR-DISPUTE-003 | M | 管理员可以记录调查结论并关闭争议。 | 关闭时必须填写处理结论；双方登录后均可查看结论和状态。 |
| FR-DISPUTE-004 | S | 管理员可要求争议双方继续补充说明。 | 状态显示为待补充，双方可以追加说明但普通用户之间仍保持匿名。 |

### 4.9 无障碍与安全交互

| ID | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-A11Y-001 | M | 按钮、输入框、菜单、列表和关键状态提供正确的无障碍名称、角色和状态。 | Narrator 能朗读控件用途、当前值、选中状态和禁用状态。`【VP-Adopted】` |
| FR-A11Y-002 | M | 全部核心功能可以只使用键盘完成。 | 不使用鼠标可完成注册、登录、发布、搜索、匹配、聊天、认领、审核、备份和争议处理。 |
| FR-A11Y-003 | M | Tab 顺序符合视觉阅读顺序，焦点始终可见。 | 焦点不进入不可见区域；弹窗关闭后返回触发控件。`【VP-Adopted】` |
| FR-A11Y-004 | M | 系统跟随 Windows 高对比度设置。 | 开启高对比度后所有核心控件和状态仍可辨识，功能不中断。 |
| FR-A11Y-005 | M | 状态、错误和必填项不能只依靠颜色表达。 | 同时提供文字、图标或无障碍状态说明。`【VP-Adopted】` |
| FR-A11Y-006 | M | 重要错误、成功提示和异步状态变化可被屏幕阅读器获知。 | 使用键盘完成操作时，Narrator 能朗读结果或提示。 |
| FR-SAFE-001 | M | 删除信息、封禁用户、注销账号、恢复备份等高风险操作必须二次确认。 | 取消确认后数据和状态不变，焦点返回安全位置。 |
| FR-SAFE-002 | M | 系统在收集个人信息前说明目的、用途和范围。 | 用户未确认说明时不能完成注册；界面提供再次查看说明的入口。 |

## 5. 业务规则与状态模型

### 5.1 信息状态

| 状态 | 含义 | 公开可见 | 可发起认领 |
|---|---|---|---|
| 待审核 | 已提交，等待管理员审核 | 否 | 否 |
| 已通过 | 审核通过，正在公开 | 是 | 是 |
| 已驳回 | 审核未通过 | 否 | 否 |
| 已解决 | 已找回或已认领 | 否 | 否 |
| 已撤销 | 发布者主动撤回 | 否 | 否 |
| 已删除 | 管理员因违规而删除 | 否 | 否 |

规则：

1. 新建信息从“待审核”开始。
2. 已通过信息被修改后，重新进入“待审核”。
3. 已通过信息可以被发布者标记为已解决或撤销。
4. 管理员删除操作属于软删除，公开端不可见，管理审计记录保留。
5. 已解决或已删除信息不能产生新的认领。

### 5.2 认领状态

| 状态 | 含义 |
|---|---|
| 协商中 | 已创建认领和专属匿名会话 |
| 已完成 | 发布者已确认完成交接 |
| 已取消 | 任一方在完成前取消 |
| 争议中 | 双方之一已提交争议 |
| 争议关闭 | 管理员已记录结论并关闭争议 |

规则：

1. 认领双方只能是信息发布者和认领发起人。
2. 信息发布者不能认领自己发布的信息。
3. 同一用户对同一条信息最多保留一项“协商中”认领。
4. 发布者确认完成时，关联信息同时变为已解决。
5. 同一信息被确认完成后，其他进行中的认领自动取消。
6. 聊天记录在认领关闭后转为只读，不随普通用户的关闭操作立即删除。

### 5.3 账号状态

| 状态 | 含义 |
|---|---|
| 正常 | 可以登录并执行业务操作 |
| 已注销 | 学生用户主动停用，不能登录 |
| 已封禁 | 管理员因违规停用，不能登录 |

账号停用采用逻辑删除。历史发布、认领、争议和审计记录仍保留，避免破坏可追溯性。

## 6. 非功能需求与量化验收标准

### 6.1 性能

| ID | 需求 | 验收标准 |
|---|---|---|
| NFR-PERF-001 | 常用查询应快速反馈。 | 在 10,000 条信息数据下，搜索或分类筛选在开发演示电脑上 1 秒内显示结果。 |
| NFR-PERF-002 | 应用启动时间可接受。 | 冷启动进入登录界面不超过 5 秒。 |
| NFR-PERF-003 | 单机写入操作应可靠且及时。 | 发布、认领、状态变更和聊天消息提交在 1 秒内显示成功或明确错误，不重复写入。 |

### 6.2 稳定性与数据完整性

| ID | 需求 | 验收标准 |
|---|---|---|
| NFR-REL-001 | 连续使用过程中不能崩溃或丢失已提交数据。 | 连续运行 2 小时并执行至少 200 次核心操作，无崩溃；已成功提交的数据重启后仍存在。 |
| NFR-REL-002 | 多表写入应保持事务一致。 | 认领完成、审核和备份恢复过程中发生异常时，不出现半完成状态。 |
| NFR-REL-003 | 应用应阻止非法状态迁移。 | 待审核信息不能直接认领；已解决信息不能重新发起认领。 |

### 6.3 安全与隐私

| ID | 需求 | 验收标准 |
|---|---|---|
| NFR-SEC-001 | 密码必须采用带盐的不可逆哈希保存。 | 数据库和日志中不存在明文密码；相同密码的不同账号产生不同哈希。 |
| NFR-SEC-002 | 校园卡号必须唯一。 | 数据库唯一约束拒绝重复绑定。 |
| NFR-SEC-003 | 所有敏感操作必须进行身份和角色校验。 | 普通用户不能调用管理员审核、用户封禁、备份恢复或查看他人私密聊天。 |
| NFR-SEC-004 | 联系方式和真实身份默认不公开。 | 公开列表和普通用户聊天界面不显示真实校园卡号、姓名和联系方式。 |
| NFR-PRIV-001 | 管理员访问私密聊天或真实身份必须可审计。 | 日志包含管理员、目标会话、争议编号、访问时间和原因；日志仅管理员可查看。 |
| NFR-PRIV-002 | 备份文件不得通过应用界面向普通用户暴露。 | 普通用户不能查看、导出或恢复备份。 |

### 6.4 兼容性与分发

| ID | 需求 | 验收标准 |
|---|---|---|
| NFR-COMP-001 | 支持 Windows 10/11 x64。 | 在至少两个受支持的 Windows 环境中自包含运行成功。 |

| NFR-COMP-004 | 单机离线运行。 | 断开网络后启动、登录、发布、匹配、聊天、审核、备份和恢复仍可使用。 |

### 6.5 无障碍

| ID | 需求 | 验收标准 |

| NFR-A11Y-004 | 文本和焦点指示达到对比度要求。 | 普通文本与背景对比度至少 4.5:1；焦点指示与相邻背景至少 3:1。 |
| NFR-A11Y-005 | 视障模式下原功能保持完整。 | 在高对比度和 Narrator 开启时，原功能仍可用、完整、不中断。 |

## 7. 数据需求

### 7.1 逻辑实体

| 实体 | 主要信息 |
|---|---|
| 用户 User | 内部 ID、校园卡号、密码哈希、显示名称、联系方式、角色、状态、注册时间 |
| 物品分类 Category | 分类 ID、分类名称、是否启用 |
| 信息 Posting | 信息 ID、类型、标题、分类、发生时间、地点、描述、图片路径、图片替代文本、发布人、审核状态、解决状态、版本号、时间戳 |
| 审核记录 ReviewLog | 记录 ID、信息 ID、管理员 ID、动作、理由、时间 |
| 认领 Claim | 认领 ID、信息 ID、发起人 ID、发布者 ID、状态、认领说明、创建时间、结束时间 |
| 聊天消息 Message | 消息 ID、认领 ID、发送人 ID、内容、发送时间、只读标记 |
| 争议 Dispute | 争议 ID、认领 ID、提交人 IDs、原因、说明、状态、管理员结论、时间 |
| 审计日志 AuditLog | 日志 ID、管理员 ID、动作、目标对象、原因、时间 |
| 备份记录 BackupRecord | 文件名、路径、类型、创建时间、完整性状态 |

### 7.2 数据规则

1. 校园卡号在用户表内唯一。
2. 一个信息可以同时存在多个“协商中”认领，但最多只能有一个“已完成”认领；确认一项后其余协商中认领自动取消。
3. 同一用户对同一信息最多有一个协商中的认领。
4. 消息必须归属于一个有效认领。
5. 争议必须关联一个已有认领。
6. 审核、封禁、删除、争议访问和恢复操作必须写入审计日志。
7. 时间统一以本机本地时间显示，数据库保留可排序的精确时间值。

## 8. 关键业务场景

### 8.1 用户注册与登录

1. 游客选择注册。
2. 系统显示个人信息采集目的、用途和范围。
3. 用户填写校园卡号、显示名称、联系方式和密码并确认说明。
4. 系统执行本地模拟验证，检查校园卡号唯一性。
5. 注册成功后用户登录并使用普通用户功能。

### 8.2 发布与审核

1. 用户提交失物或招领信息。
2. 信息进入待审核状态。
3. 管理员查看内容和图片替代文本，执行通过或驳回。
4. 只有通过的信息进入公开列表。

### 8.3 基础关联匹配

1. 用户查看某条公开信息。
2. 系统查找另一类型的公开信息，计算可解释的匹配依据和得分。
3. 系统返回最多 10 条候选，展示匹配字段。
4. 用户选择候选并手动发起认领。

### 8.4 认领与匿名沟通

1. 认领发起人从公开信息发起认领。
2. 系统创建认领及专属匿名会话。
3. 双方使用匿名编号沟通，不暴露真实联系方式。
4. 发布者确认交接完成。
5. 系统将认领标记为已完成，将信息标记为已解决，并关闭其他进行中的认领。

### 8.5 争议处理

1. 认领任一方提交争议原因和说明。
2. 管理员查看相关真实账号、认领和聊天记录。
3. 系统记录此次敏感访问。
4. 管理员填写结论并关闭争议。
5. 双方登录后可查看结论，彼此之间仍保持匿名。

### 8.6 备份与恢复

1. 应用每天首次启动时检查当日自动备份。
2. 如未备份，则创建备份并保留最近 7 份自动备份。
3. 管理员执行恢复前，系统创建当前数据的保护副本。
4. 恢复完成后校验数据库可用性，并显示结果。

## 9. 约束、假设与依赖

### 9.1 开发约束

1. 使用 VSCode 和 .NET 技术栈开发。`【Revised】`
2. 应用为本地单机版本，不建设远程服务器。
3. 数据库使用 SQLite。
4. 校园卡认证为本地模拟，不能声称接入学校真实身份系统。
5. 匹配算法采用可解释的规则匹配，不使用机器学习。
6. 应用必须可生成 Windows x64 自包含发布包。`【VP-Adopted】`
7. 团队人数和总工期尚未确定，不写入当前验收数值。

### 9.2 假设

1. 课程演示电脑为 Windows 10/11 x64，至少 4 核 CPU、8 GB 内存和 SSD。`【VP-Adopted】`
2. 演示过程中通过切换普通用户账号模拟认领双方；聊天为非实时本地消息。
3. 用户允许系统在本机保存其账号、信息、认领、聊天和审计数据。
4. 应用所在目录或用户数据目录具有写入权限。
5. 不要求多台电脑之间共享数据库。

### 9.3 外部依赖

- .NET 10 SDK（开发环境）。
- Windows Desktop Runtime（开发调试环境）。
- SQLite。
- VSCode 与 C# 开发支持（开发环境）。

## 10. 风险摘要

详细内容见同目录下的 `requirements-risk-acceptance-matrix.md`。首期最高优先级风险为：

1. 模拟认证可能被误认为真实校园身份认证。
2. 单机架构无法支持真实跨设备交流。
3. 匿名聊天与管理员审计之间存在隐私权衡。
4. 基础匹配可能产生误报。
5. 无障碍能力容易在界面迭代中回归。
6. 本地备份可能扩大敏感数据暴露面。
